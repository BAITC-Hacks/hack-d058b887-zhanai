# Архитектура «Аким на 5 часов»

## Компоненты

| Слой | Файлы | Ответственность |
| --- | --- | --- |
| Данные | `backend/data/districts.json`, `measures.json`, `rules.json` | 5 районов × 10 показателей, 14 мер, веса, бюджет, лаги, синергии, несовместимости. `data_loader.py` проверяет их при старте (5 районов, 14 мер, сумма весов и долей населения = 1, значения 0–100 и т. д.). |
| Схемы | `backend/app/schemas.py` | Pydantic с `extra="forbid"`: клиент передаёт только `measureId`, `districtId`, `eventId`, `teamName`. |
| Валидатор | `backend/app/validator.py` | Чистая функция `validate_plan` → список `{code, message, measureIds}`. |
| Симулятор | `backend/app/simulator.py` | Детерминированный расчёт: лаги, эффекты, синергии, ограничение 0–100, оценки районов, Score, критические показатели. |
| Факты | `backend/app/facts.py` | Результат → список русских предложений с числами. Их получают и модель, и шаблон. |
| AI | `backend/app/ai.py` | OpenAI Responses API со строгой JSON-схемой, проверка структуры и чисел (grounding guard), кэш, честный fallback. |
| Оптимизатор | `backend/app/optimizer.py` | Полный перебор допустимых планов, процентиль, глобальный оптимум, лучшая замена одной меры, дополнение неполного плана. |
| События | `backend/app/events.py` | 4 сценария, меняющие исходные показатели или бюджет. |
| Лидерборд | `backend/app/leaderboard.py` | SQLite `backend/data/cache/leaderboard.sqlite`, одна запись на команду. |
| Презентация | `backend/app/presentation.py` | Markdown-бриф из фактов и выводов AI. |
| HTTP | `backend/app/main.py` | FastAPI-эндпоинты, `preview`, раздача `frontend/dist` на том же порту. |
| Интерфейс | `frontend/src/**` | React 19 + TypeScript + Vite + Tailwind 4, один экран. |
| Адаптер API | `frontend/src/api/` | Единый интерфейс `Api`; реализации `http` (сервер) и `mock` (расчёт в браузере). |
| Карта | `frontend/src/components/city/CityMap.tsx`, `frontend/src/data/astanaGeometry.ts` | Контуры 5 районов Астаны из OpenStreetMap; `scripts/build_geometry.py` превращает GeoJSON в SVG-пути. |

## Поток данных

```text
Пользователь меняет план (каталог / портфель / сценарий)
   │
   ▼
usePlan → useSimulation ── POST /api/simulate {decisions, eventId}
                              │
                              ├─ events.changed_baseline(eventId) → база и бюджет
                              ├─ validator.validate_plan → errors
                              ├─ errors пусто → simulator.simulate → result (+ facts.make_facts)
                              └─ иначе, без структурных ошибок → preview (what-if)
   ◄── {valid, errors, cost, budget, event, baseline, result, preview}
   │
   ├─ панель Score, карта, плитки, портфель показывают result ?? preview
   ├─ status = valid → POST /api/improve (автоматически) → «Улучшить план», процентиль
   ├─ «AI-анализ» → POST /api/explain → simulate → facts → OpenAI → guard → ai | fallback_no_ai
   ├─ «Разыграть» → POST /api/events/draw {excludeId} → eventId в следующих запросах
   ├─ «Команды» → POST /api/leaderboard (сервер пересчитывает) → GET /api/leaderboard
   └─ «Скачать презентацию» → POST /api/presentation → akim-plan.md
```

`useSimulation` отбрасывает запоздавшие ответы, поэтому быстрые клики не перемешивают результаты. Анализ AI привязан к версии плана: если план изменился, панель помечает анализ как устаревший и предлагает «Обновить».

## API

| Метод | Путь | Кратко |
| --- | --- | --- |
| GET | `/api/health` | статус, `ruleset`, `dataVersion`, `aiConfigured`, `aiModel` |
| GET | `/api/catalog` | районы, меры, правила, `baseline`, `events` |
| POST | `/api/simulate` | проверка + `result` / `preview` |
| POST | `/api/explain` | AI-объяснение с проверкой чисел |
| POST | `/api/improve` | перебор: процентиль, оптимум, лучшая замена, дополнение |
| GET | `/api/events` | список событий |
| POST | `/api/events/draw` | случайное событие (`seed`, `excludeId`) |
| POST / GET | `/api/leaderboard` | запись / таблица команд |
| POST | `/api/presentation` | Markdown-презентация |

Полный контракт: [`api-contract.md`](api-contract.md).

## Проектные решения

**Сервер — единственный источник истины.** Стоимость, допустимость и Score считаются только на сервере; тело запроса с лишними полями (`cost`, `score`) отклоняется HTTP 422. Лидерборд и презентация заново вызывают тот же расчёт и не доверяют числам клиента. Правила (`RULESET`) задаются при запуске сервера и одинаковы для всех команд.

**`preview` отдельно от `result`.** Пользователь видит последствия каждого шага, пока план неполный: `preview` считает уникальные известные меры. Официальный `result` (а с ним AI-анализ, лидерборд, презентация, процентиль) появляется только у допустимого плана. Так интерфейс остаётся отзывчивым, и нет риска выдать недопустимый план за итог. При структурных ошибках (неизвестная мера, нет района) `preview = null`.

**Детерминированное ядро + AI-комментарий.** Числа считает код, который покрыт тестами на контрольные значения датасета (база 52.55768, пример 56.54307). AI отвечает за смысл: сильные стороны, риски, последствия, компромиссы, рекомендации. Модель получает только `facts`; ответ по строгой JSON-схеме проходит `_grounded()`: совпадает структура, `decisions` покрывают ровно выбранные меры, каждое число есть в фактах. Иначе — шаблон из тех же фактов со статусом `fallback_no_ai`. Ответы кэшируются по хэшу данных, правил, модели, версии промпта и фактов.

**Полный перебор вместо эвристики.** Допустимых планов немного (694 395 для `dataset`, 68 200 для `all_directions`), поэтому их можно перебрать все. `fast_score` — та же формула на плоских массивах, без построения ответа для UI. Тест сверяет её с `simulate` на выборке планов. Отсортированные Score кэшируются в `backend/data/cache/search-<hash данных>-<ruleset>.json`; кэш сбрасывается сам при изменении датасета. После этого процентиль — бинарный поиск, оптимум известен, лучшая замена одной меры ищется за доли секунды. Для неполного плана ищется лучшее дополнение с сохранением выбранных решений.

**События до расчёта мер.** Событие меняет исходные показатели (или лимит бюджета), после чего база и план пересчитываются по той же формуле. `/api/improve` и лидерборд работают только без события: перебор построен для исходных условий, а команды сравниваются в равных условиях.

**Адаптер API во фронтенде.** Компоненты зависят от интерфейса `Api` (`frontend/src/api/types.ts`), а не от `fetch`. Это дало три вещи:
1. интерфейс разрабатывался параллельно с сервером в режиме `mock`, где порт эталонной формулы считает в браузере;
2. форма ответов сервера приводится к типам UI в одном месте, компоненты об этом не знают;
3. переключение режима — одна переменная `VITE_API_MODE`. Для демо и проверки используется `http`: `start.sh` собирает UI именно в этом режиме.

**Один процесс для демо.** FastAPI отдаёт собранный `frontend/dist` и API на одном порту 8000: без CORS, без отдельного веб-сервера, запуск одной командой. В разработке Vite на :5173 проксирует `/api` на :8000.

**Честность данных.** Датасет синтетический. Интерфейс, презентация и промпт модели прямо говорят, что это модельные последствия, а не прогноз для реальной Астаны.
