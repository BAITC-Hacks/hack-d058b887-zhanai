# Фронтенд «Аким на 5 часов» (папка `claude.front`)

Интерфейс симулятора городских решений: пользователь выбирает пять мер, видит,
как меняются районы и итоговый Astana Quality of Life Score, получает AI-анализ
и подсказку по улучшению плана. Стек: React 19, TypeScript, Vite, Tailwind 4.

## Запуск

```bash
cd claude.front
npm install
npm run dev          # http://localhost:5173
```

Режим работы задаётся переменной `VITE_API_MODE` (см. `.env.example`):

| Режим  | Что происходит |
| ------ | -------------- |
| `mock` | По умолчанию. Расчёт, «улучшить план», события и лидерборд работают прямо в браузере по формулам датасета. Сервер не нужен. AI-пояснение собирается по шаблону из фактов расчёта и помечено «без AI». |
| `http` | Все запросы идут на `/api`. В dev-режиме Vite проксирует их на `http://localhost:8000` (см. `vite.config.ts`). |

```bash
VITE_API_MODE=http npm run dev
npm run build        # проверка типов + сборка в dist/
```

## Как устроено

```
src/
  data/dataset.ts        каталог из «Датасет районов.docx»: районы, показатели, меры,
                         синергии, несовместимости, правила, готовые сценарии, события
  api/types.ts           контракт API (совпадает с Доки/plan-akim-2-people.md)
  api/mock/engine.ts     движок для режима mock: порт эталона akim_score.py
  api/mock/index.ts      реализация API в браузере (задержки, localStorage для лидерборда)
  api/http.ts            реализация API через fetch
  lib/availability.ts    почему мера недоступна, куда её нужнее поставить
  lib/scales.ts          цветовые шкалы: синяя последовательная для оценок,
                         статусные цвета только с иконкой и подписью
  state/usePlan.ts       план из пяти решений
  state/useSimulation.ts пересчёт при каждом изменении, защита от запоздавших ответов
  components/            шапка с бюджетом, каталог, карта-схема, портфель, результат,
                         AI-панель, улучшение, событие, лидерборд, панель района
```

Числовые правила в интерфейсе не дублируются: подсказки доступности используют
только данные каталога (стоимость, лимит направления, несовместимости), а
итоговый Score всегда приходит от API. В режиме `mock` роль API играет
`api/mock/engine.ts`.

## Контракт API, на который рассчитан интерфейс

- `GET /api/catalog` → объект `Catalog` из `src/data/dataset.ts`.
- `POST /api/simulate` `{decisions, eventId}` → `SimulateResponse`. Кроме полей из
  плана интерфейс использует `preview`: тот же расчёт, что `result`, но для
  неполного или недопустимого набора, чтобы показывать последствия каждого
  шага. Если сервер не отдаёт `preview`, интерфейс покажет только валидный
  результат.
- `POST /api/explain` → `ExplainResponse` с полями `strengths`, `risks`,
  `consequences`, `recommendations`, `decisions[]`, `status: ai | fallback`.
- `POST /api/improve` → `ImproveResponse`: `percentile`, `optimum`, `swap`.
- `POST /api/events/draw`, `GET/POST /api/leaderboard`, `POST /api/presentation`
  (`{markdown}`) — дополнения; при ошибке сервера интерфейс сообщает об этом,
  расчёт продолжает работать.

Полные типы: `src/api/types.ts`.

## Дизайн-принципы

- Один экран: город реагирует на каждое решение, результат считается сразу.
- Дельты важнее абсолютных чисел: разброс Score между планами узкий.
- Недоступная мера объясняет, почему: бюджет, лимит направления, несовместимость.
- При выборе района показываются текущие значения нужного показателя, худший
  район подсвечен как «нужнее всего».
- Оценка района на карте кодируется одним оттенком (темнее = выше); критическое
  состояние помечается иконкой и подписью, а не только цветом.
- AI-пояснение опирается на факты расчёта; без ключа модели работает шаблон.
