# План разработки «Аким на 5 часов» для двух человек

Цель: за 300 минут собрать работающий симулятор городских решений по выданному датасету. Пользователь выбирает пять мероприятий, получает проверенный расчёт последствий и понятное AI-объяснение. На защите команда должна уметь изменить набор мероприятий и сразу показать новый результат.

План рассчитан на двух разработчиков: человек 1 увереннее работает с Python и данными, человек 2 — с веб-интерфейсами. Время отсчитывается от начала работы. Контрольные точки важнее количества дополнительных функций.

## Ревью плана (Claude Code, 23.09)

Контрольные числа плана проверены независимым эталонным движком `akim_score.py` (коммит `c0c6bf0`): совпадают до пятого знака, правила расчёта переданы верно. Что изменено и почему:

- Обязательная часть занимала слишком много времени. Валидатор, расчёт и полный перебор уже написаны и проверены, поэтому ядро должно быть готово к 00:45, а не к 01:15. Освободившееся время идёт на дополнения из ТЗ.
- «Улучшить план» заменён на полный перебор: 694 395 допустимых наборов считаются примерно за 7 секунд и кэшируются на диске. Это даёт глобальный оптимум, процентиль плана и лучшую замену, а не только одношаговое улучшение.
- AI-слой получает от движка готовый список фактов и проходит числовую проверку ответа. Поля ответа переименованы под формулировку must-have: сильные стороны, риски, возможные последствия.
- Из исключений убраны экспорт презентации, локальный лидерборд и события: каждый из них закрывает опциональный пункт ТЗ и стоит 20–40 минут. По-прежнему исключены регистрация, внешние сервисы, реальная карта и обучение моделей.
- Добавлены числа перебора. Демонстрацию улучшения начинаем со слабого набора: пример организаторов и так лучше 99,9 % допустимых планов, на нём улучшение почти незаметно.
- Оба участника используют AI-ассистентов (Codex, Claude Code). Каждый ассистент работает только в папке своего владельца; общие файлы правит владелец.

1. Открыть ТЗ `Доки/HackAlem AI_ «Аким на 5 часов» - AI-симулятор управления городом.docx` и датасет `Доки/Датасет районов.docx`.

3. Подтвердить знакомый команде стек. Предлагаемый вариант: Python + FastAPI на сервере, React + TypeScript + Vite в интерфейсе. Данные хранятся в JSON; база данных для MVP не требуется.
4. Зафиксировать описанный ниже формат API. Человек 2 начинает с проверочного ответа и подключает настоящий сервер к 90-й минуте.
5. Проверить доступ к разрешённому LLM API коротким запросом на нейтральном тексте. Модель задаётся через `AI_MODEL`, ключ хранится только на сервере в переменной окружения. Проверить доступ и лимиты до разработки AI-экрана. Ключи не отправлять в чат и не добавлять в Git.
6. Уточнить у организаторов, обязательны ли мероприятия из всех пяти направлений. В общем ТЗ перечислены пять направлений, но подробный датасет разрешает минимум три при ограничении «не более двух мер из одного направления». Пример из датасета охватывает четыре направления.
7. Пока уточнение не получено, использовать явно документированный режим `RULESET=dataset`: ровно пять мер, максимум две из направления. Режим `all_directions` дополнительно требует все пять направлений. Активный режим задаётся на сервере и одинаков для всех пользователей. Интерфейс показывает его название. При переключении режима прежние результаты пересчитываются. Для ответа организаторам держать под рукой число: в режиме `all_directions` лучший достижимый Score 56.34451, ниже примера из датасета.
8. Проверенный эталон валидатора, расчёта и перебора `akim_score.py` хранится в истории репозитория, в коммите `c0c6bf0`. Достать его: `git show c0c6bf0:backend/reference/akim_score.py > akim_score.py`. Формулы из него переносятся без изменений.

Оба участника работают в одном репозитории, каждый в своей ветке: `codex/akim-engine` и `codex/akim-ui`. Каждый завершённый этап фиксируется отдельным коммитом. Общие файлы изменяет назначенный владелец; изменение формата API сначала согласуется с напарником. AI-ассистент каждого участника (Codex или Claude Code) работает только в папке владельца: `backend/` у человека 1, `frontend/` у человека 2. Два ассистента не должны править один файл.

## Общий формат данных и API

Человек 1 владеет контрактом. Человек 2 использует его без самостоятельного переименования полей. Порядок решений не влияет на расчёт.

### Набор решений

```json
{
  "decisions": [
    {"measureId": "M7", "districtId": "nura"},
    {"measureId": "M8", "districtId": "nura"},
    {"measureId": "M10", "districtId": "nura"},
    {"measureId": "M12", "districtId": null},
    {"measureId": "M5", "districtId": "saryarka"}
  ]
}
```

Для городской меры `districtId` равен `null`. Пользователь не задаёт цену, эффект, балл или активный режим правил — сервер берёт их из своего датасета.

### Эндпоинты

| Запрос | Вход | Ответ |
| --- | --- | --- |
| `GET /api/health` | Нет | Состояние сервера |
| `GET /api/catalog` | Нет | Районы, показатели, меры, правила, версия данных, исходное состояние |
| `POST /api/simulate` | `decisions` | Проверка допустимости и результат расчёта |
| `POST /api/explain` | `decisions` | AI-объяснение пересчитанного на сервере результата |
| `POST /api/improve` | `decisions` | Процентиль, глобальный оптимум, лучшая замена одной меры либо сообщение, что её нет |
| `POST /api/events/draw` | `seed` (необязательно) | Событие: ID, название, эффект на показатели или бюджет |
| `POST /api/leaderboard` | `teamName`, `decisions` | Сохранённая запись с пересчитанным сервером результатом |
| `GET /api/leaderboard` | Нет | Таблица команд по Score |
| `POST /api/presentation` | `decisions` | Markdown-презентация решения |

Первые четыре эндпоинта обязательны. `improve` — дополнение 1, остальные три — дополнения 3–5 в порядке приоритета. `POST /api/simulate` дополнительно принимает необязательный `eventId`.

### Ответ расчёта

Обязательные поля: `valid`, `errors`, `cost`, `remainingBudget`, `decisionCount`, `ruleset`, `dataVersion`, `baseline`, `result`.

- `errors`: список объектов `code`, `message`, `measureIds`.
- `baseline`: `score`, `cityAverage`, `minDistrictScore`, `criticalCount` и исходные оценки районов.
- `result`: `score`, `delta`, `cityAverage`, `minDistrictScore`, `criticalCount`, `districts`, `synergies`, `decisions`, `facts`, `directionCoverage`, `missedSynergies`, `unusedBudget`.
- Каждый элемент `decisions`: `measureId`, `districtId`, `cost`, `lag`, `realizedShare` (равно `(8 − lag) / 8`), `realizedEffects` по показателям.
- `facts`: список коротких утверждений на русском с числами, из которых собирается AI-пояснение и шаблон без AI.
- Каждый элемент `districts`: `districtId`, `beforeScore`, `afterScore`, `beforeIndicators`, `afterIndicators`.
- Каждый элемент `synergies`: ID двух мер, район, показатель, фиксированный бонус.
- При нарушении правил или неполном наборе `valid=false`, `result=null`, причины находятся в `errors`.
- При неизвестном ID или неправильной структуре запроса сервер возвращает понятную ошибку валидации; расчёт по частично распознанному набору не выполняется.
- Стоимость и остаток возвращаются только там, где все ID мер распознаны. Остаток у превышенного бюджета может быть отрицательным.

Примеры кодов ошибок: `EXACTLY_FIVE_REQUIRED`, `DUPLICATE_MEASURE`, `BUDGET_EXCEEDED`, `DISTRICT_REQUIRED`, `CITY_DISTRICT_FORBIDDEN`, `DIRECTION_LIMIT`, `INCOMPATIBLE_MEASURES`, `ALL_DIRECTIONS_REQUIRED`.

### Ответ AI

Поля: `status`, `summary`, `strengths`, `risks`, `consequences`, `recommendations`, `decisions`, `model`, `cached`, `grounded`. `grounded=true` означает, что все числа в тексте прошли сверку с фактами.

`status` различает настоящий ответ модели и недоступность AI. Рекомендации с конкретным новым набором содержат проверенный результат расчёта. Кэш повторно используется только для того же набора, правил и версий. Модельный текст не меняет числовые данные симулятора.

## Правила расчёта, которые нельзя потерять

1. Все десять показателей имеют шкалу 0–100; больше означает лучше.
2. Горизонт — восемь кварталов. Реализованный эффект меры равен полному эффекту, умноженному на `(8 − lag) / 8`.
3. Районная мера влияет только на указанный район. Городская влияет на все пять районов.
4. Сначала суммируются эффекты и синергии, затем показатель ограничивается диапазоном 0–100. Это сохраняет независимость от порядка решений.
5. Синергия применяется один раз и не уменьшается из-за лага:
   - M1 + M2: T1 +2 в районе M1;
   - M10 + M12: B1 +2 в районе M10;
   - M5 + M6: E2 +2 в районе M5.
6. M1 и M3 несовместимы при любом выборе районов.
7. M4 и M7 несовместимы только в одном районе. M5 и M13 — также только в одном районе.
8. У M11 эффект T1 отрицательный: −2 до учёта лага. Его нельзя потерять при переносе данных.
9. Веса T1, T2, E1, E2, S1, S2, B1, B2, C1, C2: `0.10, 0.10, 0.09, 0.11, 0.11, 0.11, 0.09, 0.09, 0.10, 0.10`.
10. Оценка района — сумма взвешенных показателей. Оценка города — среднее оценок районов с весами по долям населения.
11. `Score = 0.7 × cityAverage + 0.3 × minDistrictScore − criticalCount`.
12. `criticalCount` — количество пар «район × показатель» со значением строго ниже 40 после всех изменений. Значение ровно 40 не штрафуется.
13. Бюджет не больше 100, ровно пять разных ID мероприятий, максимум две меры одного направления. Неиспользованный бюджет не даёт бонусных баллов.
14. Промежуточные значения не округляются. Округление до двух знаков используется только в интерфейсе. Для пороговых проверок удобно использовать `Decimal` или целые значения в единицах 1/8.
15. Вклад мер можно показывать как изменение отдельных показателей. Вклады в общий Score нельзя просто складывать: формула содержит минимум, пороговые штрафы и синергии.

## Приоритеты при нехватке времени

Порядок работы: правильная математика → полный пользовательский сценарий → настоящий AI-анализ → проверки и README → поиск улучшений → визуальная полировка.

| Ситуация | Действие |
| --- | --- |
| На 90-й минуте нет расчёта в интерфейсе | Оба чинят интеграцию. Поиск улучшений откладывается. |
| К 135-й минуте нет настоящего AI-анализа | Человек 1 завершает AI-доступ и обработку ответа; человек 2 занимается тестами и README. |
| На третьем часу основа работает, улучшения нет | Сдать обязательный сценарий качественно; кнопку улучшения не показывать до готовности. |
| Остался последний час | Новые функции не добавлять; чистый запуск, ошибки, документация, репетиция. |

Регистрацию, личные кабинеты, внешние базы данных и облачные сервисы, голосовой ввод, реальную географическую карту с тайлами и обучение моделей оставляем за пределами пятичасового MVP. Локальный JSON или SQLite для лидерборда, события и экспорт презентации допустимы: они дешёвые и закрывают опциональные пункты ТЗ.
