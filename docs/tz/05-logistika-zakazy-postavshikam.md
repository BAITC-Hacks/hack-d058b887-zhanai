# **Кейс. Автоматизация формирования заказов поставщикам**

| 1\. Название | Автоматический расчёт заказов поставщикам для пополнения склада |
| :---- | :---- |
| **2\. Проблема и ценность** | Сейчас менеджер отдела закупа рассчитывает потребность в пополнении склада вручную, консолидируя данные в Excel. Из-за трудоёмкости такого детального анализа расчёт проводится нечасто и не в режиме реального времени, из\-за чего возникают избыточные запасы по одним позициям и дефицит по другим, а разовые крупные заказы (в том числе продажи большого объёма одному клиенту) искажают расчёт регулярной потребности, что ведёт к лишним издержкам на хранение и упущенным продажам. **Ценность решения:** снижение издержек на избыточное хранение, сокращение случаев дефицита и упущенных продаж, повышение точности регулярных закупочных решений. |
| **3\. Пользователь** | **Основной пользователь:** менеджер отдела закупа. **Ключевой сценарий:** запускает расчёт по складу или категории → получает список рекомендованных заказов поставщикам с обоснованием по каждой позиции → проверяет, корректирует при необходимости → утверждает заказ. |
| **4\. Задача** | Разработать сервис, который на основе истории продаж, сезонности, устойчивого роста спроса, текущих остатков, информации по товарам в пути, категорий товаров, прогноза по приросту и оценки упущенного спроса в периоды отсутствия товара формирует рекомендованные заказы поставщикам. Сервис должен выявлять разовые крупные заказы (включая крупные продажи одному клиенту) и исключать их из расчёта регулярной потребности в запасах. |
| **5\. Вход → выход** | **Вход:** история продаж (дата, артикул, количество, обезличенный клиент, цена) за период, текущие остатки по складам, периоды отсутствия товара (stockout) по артикулам, справочник поставщиков и сроков поставки, материальная ведомость из 1С. **Выход:** список рекомендованных заказов (артикул, поставщик, рекомендуемое количество, обоснование, срочность) в виде таблицы/дашборда с возможностью экспорта. |
| **6\. Данные (если задача на основе данных)** | **Ссылка/способ доступа:** выгрузка истории продаж и остатков; партнёр предоставит отчёт V2 и данные по динамике продаж (образец предоставляется партнёром, полный набор и точная дата выдачи — по согласованию). **Поля и объём:** дата продажи, артикул, наименование, количество, цена, обезличенный ID клиента, склад, остаток на дату; история продаж за продолжительный период (порядок объёма уточняется партнёром). **Ограничения:** данные о клиентах должны быть обезличены; допустимо использование синтетических данных с реалистичным распределением для разработки и тестирования. |
| **7\. Must have** | 1\) Расчёт базовой потребности в пополнении по каждому артикулу с учётом всех предусмотренных данных (история продаж, текущие остатки, товары в пути, категории товаров, прогноз по приросту) — проверка: на тестовом наборе данных формируется корректный список позиций с рекомендуемым количеством, и расчёт не игнорирует ни один из переданных источников данных — изменение любого из них (например, объёма товаров в пути) отражается на итоговом результате. 2\) Учёт сезонности и устойчивого роста спроса при прогнозировании — проверка: для товара с выраженной сезонностью прогноз отражает сезонный паттерн, а не просто среднее значение по всей истории. 3\) Оценка и компенсация упущенного спроса в периоды отсутствия товара — проверка: для артикула с зафиксированным stockout расчётная потребность скорректирована в большую сторону по сравнению с расчётом по «сырым» фактическим продажам. 4\) Выявление и исключение разовых крупных заказов, включая крупные продажи одному клиенту — проверка: искусственно добавленный в тестовые данные разовый крупный заказ не приводит к существенному росту рекомендуемого регулярного количества. 5\) Формирование итогового списка заказов, сгруппированного по поставщикам, с кратким обоснованием по каждой позиции — проверка: каждая строка выходного списка сопровождается объяснением, почему предложено именно такое количество, и список можно просмотреть в разбивке по каждому поставщику. |
| **8\. Опционально** | Приоритизация позиций по риску дефицита; учёт минимальной партии заказа и условий конкретного поставщика; визуализация трендов спроса по категориям; автоматическая выгрузка/рассылка сформированного заказа поставщику. |
| **9\. Ограничения** | **Нельзя:** автоматически отправлять заказ поставщику без подтверждения ответственного сотрудника; использовать в расчётах неанонимизированные данные о клиентах. **Обязательно учесть:** приватность данных о продажах и клиентах, объяснимость расчёта, устойчивость алгоритма к аномалиям и выбросам во входных данных, совместимость выходного формата с текущей учётной системой компании. |

# **Кейс. Жеткізушілерге тапсырыстарды қалыптастыруды автоматтандыру**

| 1\. Атауы | Қойманы толықтыру үшін жеткізушілерге тапсырыстарды автоматты түрде есептеу |
| :---- | :---- |
| **2\. Мәселе және құндылығы** | Қазіргі уақытта сатып алу бөлімінің менеджері қойманы толықтыру қажеттілігін деректерді Excel-де біріктіре отырып, қолмен есептейді. Мұндай егжей\-тегжейлі талдаудың күрделілігіне байланысты есептеу сирек және нақты уақыт режимінде жүргізілмейді, соның салдарынан бір позициялар бойынша артық қорлар, ал басқалары бойынша тапшылық туындайды, ал бір реттік ірі тапсырыстар (соның ішінде бір клиентке үлкен көлемде сату) тұрақты қажеттілікті есептеуді бұрмалайды, бұл сақтауға кететін артық шығындарға және жіберіп алынған сатылымдарға әкеледі. **Шешімнің құндылығы:** артық сақтау шығындарын азайту, тапшылық пен жіберіп алынған сатылымдар жағдайларын қысқарту, тұрақты сатып алу шешімдерінің дәлдігін арттыру. |
| **3\. Пайдаланушы** | **Негізгі пайдаланушы:** сатып алу бөлімінің менеджері. **Негізгі сценарий:** қойма немесе санат бойынша есептеуді іске қосады → әр позиция бойынша негіздемесі бар жеткізушілерге ұсынылған тапсырыстар тізімін алады → тексереді, қажет болса түзетеді → тапсырысты бекітеді. |
| **4\. Міндет** | Сатылымдар тарихы, маусымдылық, сұраныстың тұрақты өсуі, ағымдағы қалдықтар, жолдағы тауарлар туралы ақпарат, тауар санаттары, өсім болжамы және тауар болмаған кезеңдердегі жіберіп алынған сұранысты бағалау негізінде жеткізушілерге ұсынылған тапсырыстарды қалыптастыратын сервис әзірлеу. Сервис бір реттік ірі тапсырыстарды (соның ішінде бір клиентке ірі сатылымдарды) анықтап, оларды қорларға деген тұрақты қажеттілікті есептеуден алып тастауы тиіс. |
| **5\. Кіріс → шығыс** | **Кіріс:** кезең ішіндегі сатылымдар тарихы (күні, артикулы, саны, иесіздендірілген клиент, бағасы), қоймалар бойынша ағымдағы қалдықтар, артикулдар бойынша тауар болмаған кезеңдер (stockout), жеткізушілер мен жеткізу мерзімдерінің анықтамалығы, 1С-тен материалдық ведомость. **Шығыс:** экспорттау мүмкіндігі бар кесте/дашборд түріндегі ұсынылған тапсырыстар тізімі (артикул, жеткізуші, ұсынылатын саны, негіздеме, шұғылдық). |
| **6\. Деректер (егер міндет деректерге негізделсе)** | **Сілтеме/қол жеткізу тәсілі:** сатылымдар тарихы мен қалдықтардың үзіндісі; серіктес V2 есебін және сатылымдар динамикасы бойынша деректерді ұсынады (үлгіні серіктес береді, толық жиынтық және берілетін нақты күні — келісім бойынша). **Өрістер мен көлемі:** сату күні, артикул, атауы, саны, бағасы, клиенттің иесіздендірілген ID-і, қойма, белгілі бір күнгі қалдық; ұзақ кезеңдегі сатылымдар тарихы (көлемнің реті серіктеспен нақтыланады). **Шектеулер:** клиенттер туралы деректер иесіздендірілуі тиіс; әзірлеу және тестілеу үшін шынайы үлестірімі бар синтетикалық деректерді пайдалануға жол беріледі. |
| **7\. Must have** | 1\) Барлық көзделген деректерді (сатылымдар тарихы, ағымдағы қалдықтар, жолдағы тауарлар, тауар санаттары, өсім болжамы) ескере отырып, әр артикул бойынша толықтырудың базалық қажеттілігін есептеу — тексеру: тестілік деректер жиынтығында ұсынылатын саны көрсетілген позициялардың дұрыс тізімі қалыптасады, ал есептеу берілген деректер көздерінің ешқайсысын елемей қалдырмайды — олардың кез келгенінің өзгеруі (мысалы, жолдағы тауарлар көлемінің) қорытынды нәтижеде көрініс табады. 2\) Болжау кезінде маусымдылық пен сұраныстың тұрақты өсуін ескеру — тексеру: маусымдылығы айқын тауар үшін болжам бүкіл тарих бойынша жай ғана орташа мәнді емес, маусымдық паттернді көрсетеді. 3\) Тауар болмаған кезеңдердегі жіберіп алынған сұранысты бағалау және өтеу — тексеру: stockout тіркелген артикул үшін есептік қажеттілік «шикі» нақты сатылымдар бойынша есептеумен салыстырғанда ұлғайту жағына қарай түзетілген. 4\) Бір реттік ірі тапсырыстарды, соның ішінде бір клиентке ірі сатылымдарды анықтау және алып тастау — тексеру: тестілік деректерге жасанды түрде қосылған бір реттік ірі тапсырыс ұсынылатын тұрақты санның айтарлықтай өсуіне әкелмейді. 5\) Жеткізушілер бойынша топтастырылған, әр позиция бойынша қысқаша негіздемесі бар тапсырыстардың қорытынды тізімін қалыптастыру — тексеру: шығыс тізімінің әр жолы неліктен дәл осындай сан ұсынылғаны туралы түсіндірмемен беріледі, ал тізімді әр жеткізуші бөлінісінде қарауға болады. |
| **8\. Опционалды** | Позицияларды тапшылық қаупі бойынша басымдылыққа бөлу; ең аз тапсырыс партиясын және нақты жеткізушінің шарттарын ескеру; санаттар бойынша сұраныс трендтерін визуализациялау; қалыптастырылған тапсырысты жеткізушіге автоматты түрде жүктеу/жіберу. |

Шектеулер** | **Болмайды:** жауапты қызметкердің растауынсыз тапсырысты жеткізушіге автоматты түрде жіберу; есептеулерде клиенттер туралы иесіздендірілмеген деректерді пайдалану. **Міндетті түрде ескеру қажет:** сатылымдар мен клиенттер туралы деректердің құпиялылығы, есептеудің түсіндірмелілігі, алгоритмнің кіріс деректеріндегі аномалиялар мен шығарындыларға төзімділігі, шығыс форматының компанияның ағымдағы есеп жүйесімен үйлесімділігі. |

# **Case. Automating Supplier Order Generation**

| 1\. Name | Automatic calculation of supplier orders for warehouse replenishment |
| :---- | :---- |
| **2\. Problem and Value** | Currently, a purchasing department manager calculates warehouse replenishment needs manually, consolidating data in Excel. Because such detailed analysis is labor-intensive, the calculation is done infrequently and not in real time. This leads to excess stock for some items and shortages for others, while one-off large orders (including high-volume sales to a single customer) distort the calculation of regular demand, resulting in unnecessary storage costs and lost sales. **Value of the solution:** lower excess storage costs, fewer shortages and lost sales, and more accurate regular purchasing decisions. |
| **3\. User** | **Primary user:** purchasing department manager. **Key scenario:** runs a calculation for a warehouse or category → receives a list of recommended supplier orders with a rationale for each item → reviews and adjusts if necessary → approves the order. |
| **4\. Task** | Develop a service that generates recommended supplier orders based on sales history, seasonality, sustained demand growth, current stock levels, goods in transit, product categories, a growth forecast, and an estimate of lost demand during out-of-stock periods. The service must detect one-off large orders (including large sales to a single customer) and exclude them from the calculation of regular stock requirements. |
| **5\. Input → Output** | **Input:** sales history for the period (date, SKU, quantity, anonymized customer, price), current stock levels by warehouse, out-of-stock periods (stockout) by SKU, a directory of suppliers and lead times, and a bill of materials from 1C. **Output:** a list of recommended orders (SKU, supplier, recommended quantity, rationale, urgency) as a table/dashboard with export capability. |
| **6\. Data (if the task is data-based)** | **Link/access method:** an export of sales history and stock levels; the partner will provide the V2 report and sales dynamics data (a sample is provided by the partner; the full dataset and exact release date are subject to agreement). **Fields and volume:** sale date, SKU, product name, quantity, price, anonymized customer ID, warehouse, stock level as of date; sales history over an extended period (the order of magnitude will be confirmed by the partner). **Constraints:** customer data must be anonymized; synthetic data with a realistic distribution may be used for development and testing. |
| **7\. Must have** | 1\) Calculation of baseline replenishment needs for each SKU, taking into account all provided data (sales history, current stock, goods in transit, product categories, growth forecast) — verification: on the test dataset, a correct list of items with recommended quantities is generated, and the calculation does not ignore any of the supplied data sources — a change in any of them (for example, the volume of goods in transit) is reflected in the final result. 2\) Accounting for seasonality and sustained demand growth in forecasting — verification: for a product with pronounced seasonality, the forecast reflects the seasonal pattern rather than simply the average over the entire history. 3\) Estimation and compensation of lost demand during out-of-stock periods — verification: for an SKU with a recorded stockout, the calculated requirement is adjusted upward compared to a calculation based on "raw" actual sales. 4\) Detection and exclusion of one-off large orders, including large sales to a single customer — verification: a one-off large order artificially added to the test data does not cause a significant increase in the recommended regular quantity. 5\) Generation of a final order list grouped by supplier, with a brief rationale for each item — verification: every row of the output list comes with an explanation of why exactly that quantity is proposed, and the list can be viewed broken down by supplier. |
| **8\. Optional** | Prioritizing items by shortage risk; accounting for minimum order quantities and specific supplier terms; visualizing demand trends by category; automatic export/sending of the generated order to the supplier. |
| **9\. Constraints** | **Not allowed:** automatically sending an order to a supplier without confirmation from the responsible employee; using non-anonymized customer data in calculations. **Must take into account:** privacy of sales and customer data, explainability of the calculation, robustness of the algorithm to anomalies and outliers in the input data, compatibility of the output format with the company's current accounting system. |
| **10\. Deliverables** | Repository: yes. README: yes (calculation methodology, description of the outlier exclusion algorithm, launch instructions). |
