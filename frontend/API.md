# Передача интерфейса человеку 1: требования к серверу

Интерфейс подготовлен без сервера. Его TypeScript-контракт находится в `src/api/types.ts`, клиент — в `src/api/client.ts`, полные проверочные JSON-совместимые объекты — в `src/fixtures/demo.ts`. Эти файлы принадлежат человеку 2. `Доки/api-contract.md` и сервер создаёт человек 1; этот документ предлагает конкретные формы полей, которые в плане оставались неопределёнными. Их нужно сверить при интеграции.

В интерфейсе есть два явных режима: сервер и демо. Клиент по умолчанию обращается к серверу. Демо включается пользователем и показывает фиксированный контрольный пример; произвольные планы оно не рассчитывает. Сбой сервера никогда автоматически не переключает приложение на демоданные.

## Что передать для подключения

1. Ветку или PR с сервером, команды установки/запуска и точную версию Python.
2. Адрес сервера для Vite proxy, обычно `http://127.0.0.1:8000`. Приложение обращается к относительным URL `/api/*`; адрес задаётся в конфигурации прокси. Для production нужны общий origin и маршрутизация `/api/*` к серверу, либо отдельно согласованная настройка URL/CORS.
3. Рабочие `GET /api/health`, `GET /api/catalog`, `POST /api/simulate`, `POST /api/explain`; последний обязательно работает шаблоном при отсутствии AI-ключа.
4. Примеры реальных ответов каталога, контрольного расчёта, недопустимого набора, AI и шаблона. Согласовать имена и типы с этим документом, особенно `scope`, `direction`, `synergies`, `missedSynergies`, `status`.
5. Правила `RULESET`, идентификатор `dataVersion`, способ конфигурации `AI_MODEL` и ключа только на сервере. Сами ключи в репозиторий, фронтенд или сообщения не передавать.
6. Если готов оптимизатор: поддержка `/api/improve` и `features.improve: true`. До этого поле `false` или отсутствует, кнопка скрыта.
7. Результаты расчётных тестов человека 1 и команды их запуска; затем совместно пройти `Доки/acceptance-checklist.md`.

## Общие правила протокола

- JSON с camelCase, заголовок `Content-Type: application/json`, без оболочек `data`/`payload`.
- ID районов: `esil`, `almaty`, `saryarka`, `baikonur`, `nura`; ID мер: `M1`…`M14`.
- Направления: `transport`, `ecology`, `social`, `safety`, `services`.
- Показатели: `T1`, `T2`, `E1`, `E2`, `S1`, `S2`, `B1`, `B2`, `C1`, `C2`.
- `population` — доля от 0 до 1, не проценты. `scope`: `district` или `city`. Бюджет — положительное число, в исходном датасете `100`.
- Числа — конечные JSON numbers без промежуточного округления; интерфейс округляет только отображение. Отсутствующий Score — `result: null`, никогда `0` или `NaN`.
- `ruleset`: `dataset` либо `all_directions`; активный режим определяет сервер. `dataVersion` — непустая строка версии исходных данных и правил расчёта. При изменении правил/данных обновить версию, сбросить кэш расчётов/AI/перебора.
- Неизвестные ID и сломанная структура: HTTP 422 с `{"detail":"Понятная причина"}` либо стандартным FastAPI-массивом `detail` с `msg`. Недоступность сервера: HTTP 5xx. HTML-страницы вместо JSON недопустимы.
- Обычные нарушения правил известного набора, включая неполный выбор: HTTP 200 и `valid: false`, все причины в `errors`, `result: null`.
- Сервер самостоятельно проверяет запросы и рассчитывает все числовые результаты. Фронтенд показывает предварительные ограничения, но не служит источником достоверного Score.
- Неизвестные дополнительные поля разрешены. Клиент проверяет обязательные поля и выдаёт понятную ошибку при несовместимом ответе.
- Таймаут клиента: каталог/расчёт 20 секунд; AI/улучшение 45 секунд. Смена выбора отменяет устаревшие запросы.

## GET /api/catalog

Обязательные поля:

```ts
type Catalog = {
  districts: {
    id: string; name: string; description: string;
    population: number; score: number;
    indicators: Record<string, number>;
  }[];
  measures: {
    id: string; name: string;
    direction: 'transport' | 'ecology' | 'social' | 'safety' | 'services';
    scope: 'district' | 'city'; cost: number; lag: number;
    effects: Record<string, number>;
  }[];
  indicators: { id: string; name: string; direction: string }[];
  budget: number;
  ruleset: string;
  dataVersion: string;
  baseline: Baseline;
  features?: { improve?: boolean };
};
type Baseline = {
  score: number; cityAverage: number; minDistrictScore: number;
  criticalCount: number;
  districts?: DistrictResult[];
};
type DistrictResult = {
  districtId: string;
  beforeScore: number; afterScore: number;
  beforeIndicators: Record<string, number>;
  afterIndicators: Record<string, number>;
};
```

Нужны все 5 районов, 14 мер и 10 показателей. Каждый район содержит все десять исходных значений; каждая мера — только её ненулевые полные эффекты **до учёта лага**. У M11 сохранить `T1: -2`. `description` описывает условный датасет; она может быть пустой строкой, но должна присутствовать. `lag` задаётся в кварталах, горизонт равен 8. Порядок районов и показателей из каталога сохраняется в интерфейсе.

Примеры объектов:

```json
{
  "id": "nura", "name": "Нура", "population": 0.16,
  "description": "Условный датасет: дефицит школ и поликлиник.",
  "score": 49.18,
  "indicators": {"T1":55,"T2":40,"E1":45,"E2":65,"S1":38,"S2":35,"B1":55,"B2":50,"C1":60,"C2":50}
}
```

```json
{
  "id": "M12", "name": "Единая цифровая платформа обращений",
  "direction": "services", "scope": "city", "cost": 14, "lag": 1,
  "effects": {"C2": 5}
}
```

Полный готовый каталог формы API — экспорт `DEMO_CATALOG` в `src/fixtures/demo.ts`; на сервере использовать собственную версию без суффикса `-demo`. База: `score:52.55768`, `cityAverage:56.8624`, `minDistrictScore:49.18`, `criticalCount:2`.

## POST /api/simulate

Тело запроса одинаково для `/simulate`, `/explain`, `/improve`:

```json
{
  "decisions": [
    {"measureId":"M7","districtId":"nura"},
    {"measureId":"M8","districtId":"nura"},
    {"measureId":"M10","districtId":"nura"},
    {"measureId":"M12","districtId":null},
    {"measureId":"M5","districtId":"saryarka"}
  ]
}
```

У городских мер район передаётся явным `null`. Для районных нужен существующий ID. Сервер не доверяет присланным извне стоимости, Score или текстовым фактам; таких полей в запросе интерфейса нет.

```ts
type SimulationResponse = {
  valid: boolean;
  errors: { code: string; message: string; measureIds?: string[] }[];
  cost: number | null;
  remainingBudget: number | null;
  decisionCount: number;
  ruleset: string;
  dataVersion: string;
  baseline: Baseline;
  result: SimulationResult | null;
};
type SimulationResult = Baseline & {
  delta: number;
  districts: DistrictResult[];
  synergies: {
    measureIds: string[]; districtId: string; indicator: string; bonus: number;
  }[];
  facts?: string[];
  missedSynergies?: string[];
};
```

`districts` содержит все пять районов и все десять показателей до/после. `synergies` — список только сработавших бонусов; для примера: `[{"measureIds":["M10","M12"],"districtId":"nura","indicator":"B1","bonus":2}]`. `facts` и `missedSynergies` — строки, не объекты. Расширенные поля плана (`decisions` с реализованными эффектами, `directionCoverage`, `unusedBudget`) можно вернуть дополнительно; текущий UI их не требует.

Полный правильный ответ контрольного примера: `SAMPLE_RESPONSE` в `src/fixtures/demo.ts`. Обязательные проверки: стоимость `95`, остаток `5`, Score `56.54307`, delta `3.98539`, cityAverage `58.0776`, minDistrictScore `52.9625`, criticalCount `0`. Допуск сравнения JSON: `1e-6`.

Для пустого набора, с подставленной серверной версией данных:

```json
{
  "valid":false,
  "errors":[{"code":"EXACTLY_FIVE_REQUIRED","message":"Нужно выбрать ровно 5 разных мероприятий.","measureIds":[]}],
  "cost":0,"remainingBudget":100,"decisionCount":0,
  "ruleset":"dataset","dataVersion":"dataset-v1",
  "baseline":{"score":52.55768,"cityAverage":56.8624,"minDistrictScore":49.18,"criticalCount":2},
  "result":null
}
```

Все нарушения возвращаются за один запрос. Коды: `EXACTLY_FIVE_REQUIRED`, `DUPLICATE_MEASURE`, `BUDGET_EXCEEDED`, `DISTRICT_REQUIRED`, `CITY_DISTRICT_FORBIDDEN`, `DIRECTION_LIMIT`, `INCOMPATIBLE_MEASURES`, `ALL_DIRECTIONS_REQUIRED`. `cost` и `remainingBudget` вычисляются только если известны все меры. Отрицательный остаток допустим при превышении бюджета. `DEMO_REQUIRES_SERVER` — только локальная техническая причина деморежима, серверу она не нужна.

Математика полностью у человека 1: эффекты с лагом, три синергии, три несовместимости, clamp, веса населения/показателей, штраф строго при `<40`, обе версии правил. Фронтенд её не дублирует. Обязательны независимые тесты базы, примера, бюджетов/районов/повторов/направлений, городских эффектов, отрицательного эффекта M11, порядка решений и отсутствия результата у недопустимого набора.

## POST /api/explain

Сервер заново проверяет и рассчитывает `decisions`, формирует факты и лишь затем вызывает модель. При сбое AI возвращает успешный шаблонный ответ с явным статусом. `grounded` означает сверку числовых утверждений с фактами, а не признак использования модели.

```json
{
  "status":"fallback",
  "summary":"Пояснение из рассчитанных фактов, без AI.",
  "strengths":["Критических показателей после плана: 0."],
  "risks":["В плане нет транспортных мер."],
  "consequences":["Остаток бюджета: 5."],
  "recommendations":["Сравните транспортный сценарий отдельным расчётом."],
  "model":null,"cached":false,"grounded":true
}
```

Согласуем `status: "ai"` для настоящего модельного текста, `"fallback"` для шаблона. Другие значения клиент отклоняет. UI объявляет текст AI-анализом только при `status === "ai"`. Для настоящего ответа обязательно передать непустое имя модели в `model`. Все пять текстовых разделов обязательны; пустые списки допустимы. Дополнительный список `decisions` из плана можно вернуть, но текущий UI не требует его. Не выдавать непроверенные рекомендации с выдуманным Score. Невалидный вход — HTTP 422; при отказе расчётного ядра — HTTP 5xx, существующий результат в UI сохраняется.

## POST /api/improve — опционально

Пока нет сервера, `features.improve` выключено. Если включено, эндпоинт обязателен и получает тот же запрос. Ответ:

```ts
type Improvement = {
  improved: boolean;
  decisions?: { measureId: string; districtId: string | null }[];
  result?: SimulationResult;
  cost?: number;
  percentile?: number;
  totalPlans?: number;
  optimalScore?: number;
  message?: string;
};
```

При `improved:true` поля `decisions` (ровно пять), `result` и `cost` обязательны. Это готовый, независимо валидированный сервером набор с результатом выше текущего. Интерфейс сначала показывает предложение, затем применяет его по отдельному действию пользователя. При `false` передать `message` с причиной; не присылать неподтверждённое улучшение. `percentile` — число от 0 до 100, доля допустимых планов с меньшим Score; `totalPlans` — размер пространства; `optimalScore` — точный глобальный максимум в текущих правилах и версии данных. Документировать поведение на равных Score. Если реализован только локальный поиск, не называть его глобальным оптимумом и не заполнять неподтверждённые поля.

## Совместная приёмка подключения

- Каталог загружается без деморежима и отображает активные правила.
- Контрольный пример возвращает ожидаемые числа, синергию и критические показатели.
- Изменение района приводит к новому серверному расчёту; старые Score/AI не показываются как актуальные.
- Превышение бюджета, конфликт и третья мера направления дают причины без Score.
- Сеть, HTTP 422/500, таймаут и AI fallback не теряют выбранный план.
- AI-ключ отсутствует в браузере; настоящий AI и шаблон различимы.
- Предложение улучшения не меняет выбор без отдельного подтверждения.
- README позволяет запустить оба компонента на чистом ноутбуке; реальные команды сервера и результаты расчётных тестов добавляются после передачи человеком 1.

События, лидерборд, экспорт серверной презентации и чат — последующие дополнения. Текущий интерфейс не вызывает соответствующие эндпоинты и не предполагает их наличия.
